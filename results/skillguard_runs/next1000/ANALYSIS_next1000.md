# What the scanners actually found: a findings analysis of the 1,000-skill experiment

**Companion to:** [REPORT_next1000.md](REPORT_next1000.md), which covers design, execution and headline numbers.

This document looks inside the alerts. For each tool it asks:
- what was detected;
- where in the skill it sits;
- what the source actually says;
- whether the other tools noticed the same thing.

**Ground rules.**
- **Open skills only.** Every item-level example comes from the 750 open skills. The 250 lockbox skills appear only inside aggregate counts that were computed before this analysis (`analysis/2026-11-23_040133/`). No lockbox finding was opened for this document.
- **Skill content is untrusted data.** It was read, never executed.
- **"Flag" and "alert" mean a tool output.** Whether an alert reflects real risk is a separate question that this document does not settle; where we offer a reading of the source, it is one researcher's reading and is marked as such.

**Sources.**
- Open-subset tables: `analysis/findings_open/` (generated by `analyze_findings_open.py`).
- Whole-sample aggregates: `analysis/2026-11-23_040133/summary.json`.
- File and line references point into the exported skill folders. Each skill is identified by its GitHub repository and path in the GitSkills database.

**Open-subset denominators:** 750 skills, of which 704 have all four Cisco core configurations complete.

## A. MalSkills: five "malicious" verdicts, 491 skills with operations

### A.1 Two very different outputs

MalSkills reports at two levels, and most confusion about it comes from mixing them up.

**Security-sensitive operations (SSOs)** are individual operations recognized by Semgrep rules.
- **Volume:** 491 of the 1,000 skills contain at least one, and the whole sample has 7,545 SSO findings.
- **Open subset:** 366 of 750 skills, 5,803 findings.
- **Categories (open skills):**

| SSO category | Findings | Skills |
|---|---|---|
| file_operation | 2,131 | 232 |
| sensitive_data_access | 977 | 168 |
| payload_execution | 859 | 163 |
| network_access | 833 | 134 |
| software_installation | 505 | 107 |
| system_configuration | 131 | 50 |
| cryptography | 87 | 30 |
| process_operation | 280 | 21 |

The most frequent individual rules are ordinary programming operations:
- `content_read_and_parse` (904 findings), mostly in shell scripts;
- `no-sys-exit` (418): calling `sys.exit` in Python is classed as "sensitive data access";
- `no-open` (326), `package_manager` (294), `no-subprocess-run` (112).

About 42% of SSO findings come from Markdown, i.e. code blocks and commands inside documentation; the rest come from code. By file: 1,491 in `SKILL.md`, 950 in other Markdown, 1,454 in Python, 1,268 in shell, 636 in JS/TS (`malskills_sso_file_types.csv`). **An SSO is a description of what code does, not an accusation.**

**A malicious verdict** is assigned only when SSOs, linked across a skill's artifacts, satisfy one of MalSkills' formal behavior patterns. Five skills received it: 4 open, 1 in the lockbox. In all four open cases, the verdict rests on exactly two SSOs on the **same documentation line**:
- `network_access/remote_data_receive`;
- `payload_execution` (`script_host_execution` or `proxy_execution_or_lolbin_abuse`).

These two together satisfy both `Malware_Delivery` and `Remote_Code_Execution` (`malskills_malicious_supporting_findings.csv`).

### A.2 The four open cases

**1. `riot-contributor`** (repository `leostera/riot`, `.agents/skills/riot-contributor/`)
- **Purpose:** a contributor guide for the Riot OCaml build tool, shipped inside the Riot repository itself.
- **Evidence:** `references/workflow.md:44`, under the heading "Recovering Riot":

  ```sh
  curl -SsL https://get.riot.ml | sh -
  ```

  The surrounding text says to use this when a broken workspace can no longer build itself. It is the project's own installer, on the project's own domain.
- **Cisco:** one LOW `PIPELINE_TAINT_FLOW` finding reported at line 1 of the same file, i.e. file-level, not at line 44.
- **SkillGuard V3.2:** `remote_fetch_execute` at exactly `references/workflow.md:44`, review priority medium. Also an `agent_config_modification` behavior from instructions elsewhere.
- **SkillGuard V3.1:** had no fetch-and-execute capability, so it reported only the configuration behavior.

**2. `security-review-deep`** (repository `charliecpeterson/agent-config`)
- **Purpose:** a security-review skill that catalogs scanners to install.
- **Evidence:** `references/scanner-catalog.md:152–153`:

  ```sh
  curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh | sh -s -- -b /usr/local/bin
  ```

  This and the matching Grype line are the vendor's documented install method.
- **Cisco:** has its own findings in this skill: two CRITICAL cross-file "exfiltration chain" alerts, a CRITICAL socket connection in a test file, and LOW pipeline findings at lines 12–13 of the catalog. None is at lines 152–153.
- **SkillGuard V3.2:** `remote_fetch_execute` at lines 152 and 153 (medium). Also `external_agent_launch` and `mcp_server_definition` (low) from the bundled MCP server's README.

**3. `skill-dbedbbc4a467`** (repository `pinshuai/literature-review-skill`)
- **Purpose:** a literature-review skill whose README explains how to install a companion paper-search MCP server.
- **Evidence:** `README.md:118`:

  ```sh
  brew install uv          # macOS; or: curl -LsSf https://astral.sh/uv/install.sh | sh
  ```

  The pipe-to-shell is the alternative install route for the `uv` package manager, written as a comment.
- **Cisco:** no related finding. It reported metadata-level issues: misleading description, undeclared network use, grep not in `allowed-tools`, an unpinned requirement.
- **SkillGuard V3.2:** `remote_fetch_execute` at `README.md:118` and `:170` (low). Also tool pre-approval, MCP-related configuration instructions and an approval-bypass phrase.

**4. `cafci-fondos-comunes-argentina`** (repository `ferminrp/agent-skills`)
- **Purpose:** queries public data on Argentine mutual funds.
- **Evidence:** `SKILL.md:135`:

  ```sh
  curl -s "https://estadisticas.cafci.org.ar/fondos/${FONDO_ID}?clase=${CLASE_ID}" | python3 -c "
  import sys, re, html, json
  h = sys.stdin.read()
  ...
  ```

  Here the downloaded HTML is piped into `python3 -c` **as input data**. The program that runs is the inline parser written in the skill; nothing downloaded is executed.
- **Cisco:** two CRITICAL `COMPOUND_FETCH_EXECUTE` and two `BEHAVIOR_BASH_TAINT_FLOW` findings, at lines 28–29 and 40–41. Those are `curl … -o "$CATALOG"` downloads in the setup block, which a bundled Python script later parses. It did not flag line 135.
- **SkillGuard V3.2:** recorded line 135 only as `network_fetch`, a supporting capability with no review priority. **This is deliberate.** `curl … | python3 -c "<code>"` is one of the false-positive patterns we found on real skills during V3.2 development, and a regression case in our benchmark now checks that V3.2 does not report it as fetch-and-execute.

### A.3 What the four cases teach

- **The malicious verdicts track a syntactic structure, not intent.** In three cases the structure, remote content piped to a shell, really is a remote-code-execution pattern. It is the widely used, widely criticized way of installing developer tools, and the URLs are the projects' official installers. In the fourth case the structure matches but the semantics differ: the interpreter runs local code on downloaded data.
- **All four triggers sit in documentation:** two reference files, a README, and a `SKILL.md` code block. MalSkills' Markdown extraction (the part broken on macOS, report section 6.1) is what makes these verdicts possible at all.
- **SkillGuard and MalSkills point at the same lines in three of four cases.** They draw different conclusions, though:
  - MalSkills issues a binary malicious verdict.
  - SkillGuard records a reviewable behavior, at medium or low priority because the evidence is a documented installation example rather than code the skill runs.
- **Cisco's alerts in the same skills mostly concern different lines.** Cisco is not blind to fetching; in `cafci` it flagged the download-then-parse flow. But it did not report any of the four pipe-to-interpreter lines with a finding at that line.

Whether any of these skills is harmful would require looking at the installers themselves and at the repositories' history. That is beyond static scanning and beyond this experiment.

### B.3 Examples from the open subset

Each example gives the finding, what the source contains, and what the other tools reported within three lines.

**1. A pattern match on a string literal**: `testing-for-xss-vulnerabilities-with-burpsuite` (`26zl/cybersec-toolkit`, 28 stars).
- **Cisco:** `COMMAND_INJECTION_EVAL`, CRITICAL, `scripts/agent.py:143`.
- **Source line:** `weaknesses.append("unsafe-eval allows eval()")`, part of a function that audits a website's Content-Security-Policy header. The line appends a message containing the text `eval()`; there is no call to `eval`.
- **Other tools:** neither has anything at this line.

This is the clearest case in our sample of a CRITICAL label that the source line does not support.

**2. A real shell command built from a variable**: `agent-task-orchestration` (`northseadl/norix-skills`).
- **Cisco:** `COMMAND_INJECTION_EVAL`, CRITICAL, `scripts/lib/server.mjs:144`.
- **Source line:** ``exec(`${cmd} ${url}`)``. It opens a local dashboard in the browser, with `cmd` set to `open`, `start` or `xdg-open`. The command string is built by interpolation, which is the pattern command-injection rules exist to catch. The risk depends on where `url` comes from.
- **MalSkills:** `payload_execution/no-child_process-exec` at the same line.
- **SkillGuard V3.2:** nothing at this line. Generic process execution is not one of its agent-specific capabilities. In this skill it reports `external_agent_launch` (low) for documented `codex` command patterns in `references/codex-patterns.md`.

**3. An import flagged as command injection**: `blog-smoke-tests` (`openhive-network/denser`).
- **Cisco:** `COMMAND_INJECTION_JS_CHILD_PROCESS`, CRITICAL, `scripts/smoke-runner.mjs:7`.
- **Source line:** `import { spawn } from 'child_process';`. The rule fires on the import, before any call.
- **Other tools:** neither reports this line. SkillGuard reports the skill's unscoped `allowed-tools: …Bash…` pre-approval instead.

**4. A reachability check labeled exfiltration**: `vercel-deployment` (`vanman2024/dev-lifecycle-marketplace`).
- **Cisco:** two findings at `scripts/deploy-to-vercel.sh:129`:
  - `BEHAVIOR_BASH_TAINT_FLOW`, CRITICAL, "sensitive data exfiltration via network";
  - `CORRELATED_SENSITIVE_NETWORK_FLOW`, HIGH.
- **Source line:** `if curl -sf -o /dev/null "$DEPLOYMENT_URL"; then`. It checks whether the freshly deployed site responds, and discards the output. What the data-flow analysis treats as sensitive is the deployment URL captured from the Vercel CLI.
- **MalSkills:** `network_access/remote_data_receive` at the same line.
- **SkillGuard V3.2:** `network_fetch` (supporting, not reviewable) at the same line.

All three tools see the same operation, and they disagree on how much it matters.

**5. A default credential in code**: `exploiting-active-directory-with-bloodhound` (`jukeyman/jukeyman-skills`).
- **Cisco:** `SECRET_PASSWORD_VAR`, MEDIUM, `scripts/agent.py:68`.
- **Source line:** `def query_neo4j(query, uri="bolt://localhost:7687", user="neo4j", password="bloodhound")`. This is a real hard-coded credential, the conventional default for a local BloodHound database.
- **Other tools:** neither reports it. SkillGuard's `embedded_secret` detector targets API keys and tokens in agent configuration, and treats sample or placeholder values as non-secrets.

**Counter-example from the same rule:** in `find-skills` (`agentscope-ai/AgentTeams`, 5,076 stars), Cisco flags `password="${AGENTTEAMS_NACOS_PASSWORD:-}"`. That line reads an environment variable and contains no secret.

**6. Declared permissions: Cisco and SkillGuard look at the same field from opposite sides**: `gws-doc-action-extractor` (`aipcc-cicd/claudio-skills`).
- **Cisco:** `ALLOWED_TOOLS_BASH_VIOLATION` (HIGH), "code executes bash but Bash tool not in allowed-tools".
- **The skill's metadata:** it declares `allowed-tools: Bash(gws drive files list:*),Bash(gws drive files get:*),…`. Bash *is* declared, restricted to specific command prefixes. Cisco's check does not recognize the scoped `Bash(pattern)` grammar.
- **SkillGuard V3.2:** parses the grammar and records `tool_preapproval` with review priority *none*, because the grant is narrow.

Cisco warns when a skill under-declares tools. SkillGuard warns when a skill pre-approves an unscoped shell, as in `vercel-deployment` above (`unscoped_shell`, medium).

**7. YARA text rules.**
- **`app-tour`** (`hajimism/app-tour`): Cisco reports `YARA_prompt_injection_generic`, CRITICAL, at `setup.md:3`. The line reads "**Agent executes this workflow** … Do not tell the user to copy files by hand…": imperative, agent-directed text. SkillGuard reports a related `approval_bypass_instruction` (low) at `SKILL.md:41` ("do not ask the user to degit manually"). Two tools independently notice instructions that reduce user involvement.
- **`recipe-qa-rules`** (`tekliner/improvado-…`): Cisco reports `YARA_jailbreak_generic`, HIGH, at `SKILL.md:17`. That line is a heading about querying `system.tables`, and we found no jailbreak-like text there. YARA line attribution may be approximate, so we record this as unexplained, not as a false positive.

### B.4 The ATR rule pack

**Volume (open subset):**
- **Coverage:** ATR rules produced 30,074 non-informational findings in 716 of 750 open skills, with a median of 17 per skill.
- **Severity:** CRITICAL 5,022, HIGH 3,540, MEDIUM 5,154, LOW 16,358.
- **Where:** every one of them sits in a Markdown file: 18,176 in `SKILL.md`, 11,898 in other Markdown.

**Why there are so many.** The rule descriptions (read from the local raw reports) show that ATR rules were written for runtime agent traffic: tool calls, MCP arguments, model messages. Applied to static skill documentation, they match ordinary tokens:

| Rule | Findings (open) / skills | Rule's stated purpose | What it matched in a typical skill |
|---|---|---|---|
| ATR_2026_00099 | 16,344 / 695 | agent invokes a high-risk tool without human confirmation in the current turn | the word `bash` (a code-fence language tag) |
| ATR_2026_00061 | 5,069 / 479 | MCP skill behavior diverges from its description | `$TOKEN` in an example `curl` header |
| ATR_2026_00066 | 1,875 / 218 | injection through MCP tool arguments | template syntax such as `${asset_id}` |
| ATR_2026_00063 | 851 / 197 | multiple skills chained into an attack | the word `Upload` in a numbered workflow |
| ATR_2026_00012 | 772 / 213 | unauthorized tool-call attempts | `$TOKEN` |
| ATR_2026_02010 | 724 / 46 | emoji-only prompt-injection payloads | emoji in headings or lists (451 findings in one skill) |

Without ground truth we do not call these false positives, but the mechanism is clear: the rules' context assumptions do not hold for documentation. As a consequence, ATR "agrees" with SkillGuard at 97 of 246 SkillGuard locations in the comparable skills (72 of 180 in the open subset), and it flags 39 of the 40 open skills that only SkillGuard flags among the three main tools. Agreement with a detector that fires almost everywhere carries little information.

## C. SkillGuard V3.2: what we are building and what it found

### C.1 Purpose

SkillGuard does not try to be a better generic code scanner. Cisco and MalSkills already recognize network calls, subprocesses and file access, and section B shows they mostly agree with each other on those.

SkillGuard asks a narrower question that matters specifically for agents: **does this skill change what the agent is allowed to do, what it is configured to do, or who oversees it?** It therefore reads the places where agent-steering lives:
- the `allowed-tools` frontmatter;
- natural-language instructions;
- agent configuration files (Claude settings, MCP lists, Codex config, VS Code tasks, package hooks);
- scripts, in Python, shell, PowerShell and JavaScript/TypeScript.

It links what it finds across files.

**Every behavior carries:**
- a capability and a taxonomy category (T1–T9);
- an *evidence level*:
  - `code`: the skill's own code does it;
  - `config`: a configuration file declares it;
  - `skill_metadata`: frontmatter;
  - `instruction_only`: prose tells the agent to do it;
  - `documented_example`: a code block or command example;
- separate severity, confidence and review-priority fields.

Supporting capabilities (plain network send and fetch) and context signals (in-host delegation) are recorded but are not "reviewable".

**In the open subset**, V3.2 reported 188 reviewable behaviors (`sg32_capabilities.csv`), plus 257 non-reviewable ones (`sg32_non_reviewable_capabilities.csv`): network fetch 121, network send 67, in-host delegation 36, narrow tool pre-approvals 32, one endpoint override.

### C.2 Capabilities, with examples from open skills

**Agent configuration modification** (T3.3; 59 behaviors in 54 open skills; 90 in the whole sample)
- **What it is:** the skill writes, or tells the agent to write, the agent's own instruction or settings files: `CLAUDE.md`, `AGENTS.md`, `.claude/settings*.json`, `~/.codex/config.toml`, agent and skill directories.
- **Why it matters:** those files persist across sessions and steer every later task. A skill that edits them can change the agent's behavior long after the skill has finished.
- **Legitimate use:** a memory or setup skill that records project conventions.
- **Concerning use:** silently adding standing instructions or permissions.
- **Detection:** file writes in code (configuration path classes, including JS/TS `fs` calls) and instruction sentences that pair a write verb with a configuration target.
- **Open examples:**
  - `design-phase`, `SKILL.md:172`: "After user approval, append to CLAUDE.md". A write, gated by approval.
  - `setup`, `SKILL.md:57`: "Show the exact JSON snippet to add to `~/.claude/settings.local.json`". It changes settings, through the user.
  - `public-docs-sync`, `scripts/smoke_public_docs_sync.py:55`: creates `.codex/project/profiles/…` inside a temporary test repository. A low-stakes write.
- **Imprecision:** 37 of the 59 open behaviors are `instruction_only`, and that layer is noisy:
  - `revise-post` ("Read `.claude/ghost.local.md`") is a read, not a write;
  - `build` (`write docs/build/claude.md`) matched the filename `claude.md` in a documentation folder.

**Tool pre-approval** (T2.2; 39 reviewable plus 32 narrow in open skills; 53 reviewable in the whole sample)
- **What it is:** the skill's `allowed-tools` frontmatter grants tools without per-use confirmation while the skill is active.
- **Why it matters:** an unscoped `Bash` grant removes the human checkpoint for any shell command the skill's instructions or scripts lead to.
- **Legitimate use:** a build or test skill that must run many commands.
- **Concerning use:** combining the grant with instructions to run downloaded or external code.
- **Detection:** V3.2 parses the `Tool(pattern)` grammar. Scoped grants such as `Bash(gws drive files list:*)` get review priority none. Unscoped `Bash` gets medium with the risk indicator `unscoped_shell`.
- **Open example:** `plan-multi-agent-review`, `SKILL.md:4`: `allowed-tools: Bash, Read, Write`. This becomes important in combination; see the chains below.

**Approval-bypass instructions** (T2.1; 28 in open skills; 36 in the whole sample)
- **What it is:** prose or flags that tell the agent to skip confirmations or to run another agent in an auto-approve mode.
- **Why it matters:** human confirmation is the main oversight mechanism in today's coding agents.
- **Legitimate use:** documenting a tool's `--full-auto` flag for a sandboxed CI job.
- **Concerning use:** instructing the agent to relaunch itself without permission checks.
- **Detection:** a phrase lexicon with negation checks, and a separate list of agent-specific permission flags.
- **Open examples:**
  - `skip-flag`, `SKILL.md:5`: "Relaunch the agent with `--dangerously-skip-permissions` for this workflow."
  - `claude-parity`, `SKILL.md:23`: "Execute the flow directly (do not ask for unnecessary confirmation)."
  - `codex`, `SKILL.md:32`: documents `--full-auto`.
- **Imprecision:** negation handling misses several phrasings, so this detector over-reports. Examples:
  - `v1-0`, `SKILL.md:578`: "Do not overwrite existing `research/icp.md` **without asking the user first**";
  - `oci-functions-deploy`, `SKILL.md:69`: "Never slugify a descriptive phrase into a function name without asking the user".

  Both lines *require* confirmation, yet both were flagged (low priority).

**External agent launch vs in-host delegation** (T2.4)
- **What it is:** an external agent launch starts a *separate agent CLI* (`codex exec`, `claude -p`, `copilot -p`, `grok`, `opencode run`) as a subprocess. In-host delegation is the agent using its own sub-agent mechanism (Task / Agent tool, `subagent_type`).
- **Why the distinction matters:**
  - An external agent has its own permission model, configuration and credentials, and the launching skill often sets its flags.
  - Ordinary sub-agent delegation stays inside the host agent's permission system.
- **Detection:**
  - V3.1 reported both as `nested_agent_invocation`.
  - V3.2 records in-host delegation as a context signal (36 open behaviors, e.g. `design-phase`: "Spawn one sonnet sub-agent per component").
  - V3.2 reports external launches as reviewable (23 open behaviors in 19 skills). Priority rises when bypass flags are present.
- **Open examples:**
  - `skill-855d19709c57` (`texiwustion/s-capture-loop`), `scripts/capture-loop.sh:32`: `codex exec --yolo "$(cat "$SKILL_MD")"`. It runs Codex with approvals and sandbox disabled, using the skill's own instructions as the prompt. **High.**
  - `request-council-review` (`mistakenot/skills`), `SKILL.md:89` and `references/delegating-to-agents.md:256–258`. It launches Claude Code, Codex and Grok for a "council review"; the reference table lists `--dangerously-skip-permissions` and `--permission-mode bypassPermissions --always-approve` as the flags to use. **High.**
  - `plan-multi-agent-review` (`surajssd/dotfiles`), `scripts/run_reviewer.sh:288`: `copilot -p "" --allow-all-tools …`. **High.** Commendably, the skill's own `SKILL.md:219–222` explains which reviewers can and cannot be made read-only.

**Agent hooks and MCP server configuration** (T3.1/T3.2; 15 MCP definitions and 4 hook commands in the whole sample)
- **What it is:** hooks are shell commands an agent runs automatically on events. MCP servers are programs the agent starts to obtain tools.
- **Why it matters:** both execute code with the agent's privileges, outside the conversation.
- **Legitimate use:** a formatter hook; a documented MCP integration.
- **Concerning use:** an unpinned `npx` server that changes under the user's feet; a hook that sends data out.
- **Detection:** structural parsing of JSON/JSONC, YAML, TOML and INI configuration, plus configuration snippets in Markdown.
- **Open example:** `mcp-client`, `references/mcp-config.example.json:3–21`. It defines MCP servers launched with `npx @playwright/mcp@latest` and similar commands, giving `mcp_server_definition` plus `unpinned_package_execution` (`@latest`), both low.
- **Hooks:** all four whole-sample hook-command detections fall in the lockbox, so we give no example.

**Scheduler invocation and OS persistence** (T3.5; 11 scheduler and 2 persistence behaviors in open skills)
- **What it is:** cron, launchd, systemd or Task Scheduler entries, i.e. anything that makes something run again later without the agent.
- **Why it matters:** persistence outlives the session in which a user approved it.
- **Legitimate use:** a nightly report job.
- **Concerning use:** scheduling an unattended agent run with approvals disabled.
- **Detection:** scheduler commands in code and examples. `systemctl` counts only for `enable` / `link` / `reenable`, a fix for false positives found during development.
- **Open examples:**
  - `skill-855d19709c57`, `scripts/install.sh:41`: `(crontab -l …; echo "$CRON_ENTRY") | crontab -`, installing a daily 21:00 job.
  - `denario…`, `scripts/research_init.py:97`: `subprocess.run("crontab -e -f …", shell=True)`.
  - `configuring-suricata…`, `SKILL.md:274`: `sudo tee /etc/systemd/system/suricata.service` (os_persistence_write, a documented example).

**Credential access** (T4; 3 agent-credential, 2 developer-credential and 1 embedded-secret behavior in open skills)
- **What it is:** reading credential stores: agent OAuth files such as `~/.claude/.credentials.json` and `~/.codex/auth.json`, or developer credentials such as `~/.docker/config.json`, cloud CLIs and SSH keys.
- **Why it matters:** a skill that reads agent credentials can act as the user's agent elsewhere.
- **Detection:** credential-path classes with a reader-command gate; existence tests such as `[ -f ~/.aws/credentials ]` do not count.
- **Open examples:**
  - `oci-functions-deploy` (`norvik-intelligence/Norvik`), `scripts/common.sh:342–384`. A function `docker_registry_auth_probe` opens `$HOME/.docker/config.json`, reads its `auths`, `credHelpers` and `credsStore` entries, and probes the registry. **High.** It reads real credentials, and the purpose (checking registry login before a deploy) is plausible.
  - `codex-counsel`, `references/codex-cli.md:94`: mentions `~/.codex/auth.json` while explaining CLI login (instruction-only, medium).

**Fetch and execute** (T6.1; 4 behaviors in open skills, 7 in the whole sample)
- **Detection:** a download piped into a shell or interpreter that executes it, or a download followed by execution of the downloaded file.
- **Open examples:** the three MalSkills cases in section A.2.

**Risky combinations across files (chains)** (50 in the whole sample; 39 in open skills)
- **What it is:** a chain links behaviors that are individually common but significant together.
- **Rules that fired in open skills** (`sg32_chains.csv`):
  - `bypass_with_external_agent` (unscoped pre-approval or bypass instruction + external agent launch): 28 chains in 3 skills;
  - `instruction_runs_sensitive_script` (instructions that invoke a script containing a sensitive behavior): 8 in 5;
  - `preapproved_shell_runs_sensitive_script`: 2 in 1;
  - `scheduled_agent_run`: 1 in 1.
- **Open examples:**
  - `skill-855d19709c57`: `scheduled_agent_run` connects `install.sh:41` (cron) to `capture-loop.sh:32` (`codex exec --yolo`), i.e. a daily unattended agent run with approvals off. Neither file alone shows this; the chain is the useful evidence.
  - `design-html` (`uzumaki-inc/uzustack`): `bypass_with_external_agent` combines `allowed-tools: - Bash` (`SKILL.md:22`) with `SKILL.md:128`, which says that in plan mode `codex exec` / `codex review` are always allowed. **High.**
- **Imprecision:** chains are generated per pair of behaviors, so one skill (`plan-multi-agent-review`) produced 16 chains. Reporting should collapse them per skill and rule.

### C.3 The nine high-priority skills

Nine skills received high review priority: five open, four in the lockbox (not discussed).

| Open skill | What drives "high" | Cisco | MalSkills |
|---|---|---|---|
| `skill-855d19709c57` | `codex exec --yolo` on the skill's own prompt + daily cron (chain) | not flagged | SSOs (file ops, `scheduled_persistence` at the cron line); benign |
| `plan-multi-agent-review` | unscoped `Bash` + launches 6 agent CLIs, one with `--allow-all-tools` | flagged (env dump, grep not declared), not at these lines | SSOs; benign |

**What these five have in common:** **delegating work to other AI agents with their safeguards reduced, or reading credentials.** In every case the behavior serves the skill's stated purpose: multi-agent review, scheduled capture, deployment. SkillGuard's priority says *this deserves a human look*, not *this is malicious*.

**No other tool singled these skills out.** Cisco flagged three of them, but for other lines.

## D. The 53 skills only SkillGuard flags

On the 930 skills usable by all three tools, 53 are flagged by SkillGuard V3.2 and by neither Cisco core nor MalSkills' SSO layer. **40 of these are open** (`sg32_only_skills.csv`).

**By stratum:**

| Stratum | Skills |
|---|---|
| supporting_no_scripts | 19 |
| skill_md_only | 17 |
| scripts | 4 |

That alone explains much of the gap. The other tools mostly analyze code, and these skills have little or none.

**By capability** (a skill can appear twice; `sg32_only_skills_by_capability.csv`):

| Capability | Skills | Evidence |
|---|---|---|
| tool_preapproval | 15 | `allowed-tools` metadata (unscoped `Bash`) |
| agent_config_modification | 15 | 14 instruction-only, 2 documented examples |
| approval_bypass_instruction | 11 | instruction-only |
| external_agent_launch | 2 | documented examples |
| scheduler_invocation, mcp_server_definition, agent_endpoint_override | 1 each | instruction / documented example |

**Where the evidence comes from:**
- **Origin:** almost entirely `SKILL.md` and other Markdown, i.e. metadata and instructions. None of the 40 rests on executable code.
- **Breadth:** 34 of the 40 skills have a single reviewable capability. Only one has a chain, so cross-file analysis contributed little *to this group*. Its value showed up in the high-priority skills instead (section C.3).

**What V3.2 added.** Two capabilities account for most of the group, and V3.1 had neither:
- the `allowed-tools` parser (15 skills);
- the configuration-snippet and endpoint detectors (e.g. `guide-client-config`, which sets `ANTHROPIC_BASE_URL` to `http://localhost:8080`).

The instruction detectors existed in V3.1 already.

**What remains uncertain.** We read the evidence line of every behavior in the 40 open skills. **This was an informal single-reader check, not a validated labeling exercise**, so the counts below are indicative only:
- **Tool pre-approval (15):** all 15 are accurate readings. The skill does pre-approve unscoped `Bash` (e.g. `ns-stdlib`: `allowed-tools: Read, Grep, Glob, Bash`). Whether this matters depends on what the skill then does.
- **Agent configuration modification (15):**
  - About 8 describe real writes to agent configuration (append to `CLAUDE.md`, add an MCP block to `~/.codex/config.toml`, create files in `~/.config/opencode/agents/`, update `settings.local.json`).
  - About 5 only read or mention such a file.
  - 1 matched an unrelated `claude.md` filename; 1 is ambiguous.
- **Approval bypass (11):**
  - About 5 genuinely reduce confirmation (`--dangerously-skip-permissions`, `--full-auto`, "do not ask for unnecessary confirmation", `--quick` skips confirmation).
  - About 5 are rubric text, a different sense of "confirm" ("never confirm money moved…"), or negated requirements.
  - 1 is a minor convenience instruction.

**Conclusion for this group:** the 53 are not confirmed problems, and they are not misses by the other tools, which were never designed to look at these signals. They show that SkillGuard covers a distinct class of agent-steering content. Its instruction-level detectors need better precision before their counts can be read as prevalence.

## E. SkillGuard V3.1 vs V3.2

### E.1 What changed

| Area | V3.1 | V3.2 |
|---|---|---|
| Taxonomy | flat capability list | nine categories (T1–T9) with subcategories; three layers (capability, risk indicator, confirmed issue); severity, confidence and review priority as independent fields; supporting capabilities separated |
| Agent delegation | one capability, `nested_agent_invocation` | split into `in_host_delegation` (context) and `external_agent_launch` (reviewable) |
| Permission flags | generic list | per-agent flags (e.g. `--force` counts only for cursor-agent) and value-dependent flags (`--permission-mode bypassPermissions`, `--sandbox danger-full-access`) |
| `allowed-tools` | not parsed | `Tool(pattern)` grammar parsed; scoped vs unscoped shell distinguished |
| Configuration files | treated as data, not analyzed | JSON/JSONC, YAML, TOML, INI parsed; Claude settings, hooks, MCP servers, Codex config, VS Code tasks, package hooks, registries, endpoints, secrets (redacted) |
| JavaScript/TypeScript | not analyzed | tree-sitter analysis of `child_process`, `execa`, `zx`, Bun/Deno spawn, `fs` writes, `process.env`, network calls, eval of downloaded content |
| Cross-file evidence | none | instruction-to-script links (executes vs references) and 8 chain rules |
| Reporting | behavior list | schema 5.0 with explanations, remediation, evidence levels, and a per-file coverage report |

The development evaluation (65 synthetic benchmark cases, 141 checks, and a regression on 1,216 earlier skills) is in [REPORT_v32.md](../v32_regression/REPORT_v32.md). On that earlier sample, files not analyzed fell from 1,235 to 397.

### E.2 What changed on the new skills

Over all 1,000 skills, the versions agree on 912 (785 flagged by neither, 127 by both). V3.2 newly flags 58 and stops flagging 30. In the open subset the numbers are 42 and 21 (`v31_v32_changed_skills.csv`; figure 4).

**Why V3.2 flags 42 open skills that V3.1 did not:**
- 32 have a reviewable `tool_preapproval`. V3.1 never read `allowed-tools`.
- The other 10 come from new detectors:
  - endpoint overrides (`guide-client-config`, `agent-browser`);
  - an MCP onboarding snippet with an embedded key and an unpinned server (`gdex-onboarding`);
  - a systemd unit (`configuring-suricata…`);
  - a credential-path detector (`deploying-honeytokens…`);
  - a scheduler in a hosting runbook (`secure-linux-web-hosting`);
  - a fetch-and-execute installer line (`skill-60493f46628f`);
  - an MCP server definition (`roblox-mcp`);
  - two configuration writes, one of them in JavaScript (`skill-0b3447a4aa93`, `scripts/codex-pomodoro-arena.js:17`, found by the new JS/TS analyzer).

**Why V3.2 stopped flagging 21 open skills:** every one was flagged by V3.1 only for `nested_agent_invocation` and contains only in-host delegation, e.g. `readme` (`subagent_type: "general-purpose"`). V3.2 still records these, but as context. This is a deliberate narrowing: using the host agent's own sub-agents does not escape its permission model.

**Where the capabilities moved** (open subset, figure 4):
- V3.1's 55 `nested_agent_invocation` behaviors became 23 reviewable `external_agent_launch` behaviors, plus 36 non-reviewable `in_host_delegation` behaviors.
- Configuration modification (60 → 59) and approval bypass (28 → 28) stayed stable.

**The new parsers mainly improved coverage on this sample, not detections.**
- **JS/TS:** V3.2 parsed 184 of 186 JS/TS files in open skills (2 with parse errors), but only one reviewable behavior came from JS/TS.
- **Configuration:** of 342 configuration files, 339 were parsed. 317 contain no agent settings, and the reviewable configuration behaviors come from one example MCP config.

This is a useful negative result. Agent-steering in this population lives overwhelmingly in instructions and metadata, not in configuration files or JavaScript.

## What this means for the project

1. **The three tools measure different things.**
   - Cisco and MalSkills largely agree on code operations.
   - MalSkills' malicious verdict is rare and, here, driven by installer one-liners in documentation.
   - SkillGuard reports agent-control behaviors that the others do not target.
   - "Which tool finds more" is therefore the wrong question; "what does each tool see" is the right one.
2. **The most interesting SkillGuard evidence is in combinations:** pre-approved shells plus external agents launched with bypass flags, or a cron job that starts an unattended agent. These are the cases worth bringing to human reviewers first.
3. **The weakest part of SkillGuard is the instruction-level lexicon**, specifically negation and read-vs-write. It produces most of the SkillGuard-only alerts, so its precision determines how far the "distinct coverage" claim holds.
4. **Next step:** a small, protocol-driven review that samples alerts from each tool's distinct and shared regions and uses the lockbox for the final evaluation. That would turn these observations into measured precision.
